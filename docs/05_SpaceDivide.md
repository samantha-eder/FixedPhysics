# 第五层:粗相空间划分层设计笔记

本层位于 `FixedPhysics/BroadPhase` 目录下, 包含顶层接口 `IBroadPhase`、潜在碰撞对结构体 `ColliderPair`, 以及三大空间划分流派的具体实现:`SpatialHash`、`Octree`、`BVH` 

## 1. 为什么要做空间划分与顶层契约设计

当场景中存在 $N$ 个碰撞体时, 如果直接两两进行第四层的窄相精确检测(SAT 或 GJK/EPA), 时间复杂度为 $O(N^2)$ 当同屏物体达到 1000 个时, 每帧需要执行约 50 万次窄相检测, CPU 会直接卡死 

粗相(Broad-Phase)的唯一目标:只利用物体外层的轴对齐包围盒 `FPBounds`(AABB), 以接近 $O(N)$ 的极低开销过滤掉 99% 绝不可能相撞的物体对, 仅将包围盒发生重叠的潜在碰撞对 `List<ColliderPair>` 移交给第六层 

### 1.1 IBroadPhase 接口契约与零 GC 准则
外层物理世界不关心底层是网格还是树, 统一通过 `IBroadPhase` 交互:
- `Add` / `Remove` / `Clear` / `Update`:维护空间结构中的碰撞体生命周期 
- `GetPotentialPairs(List<ColliderPair> results)`:收集当前帧所有 AABB 重叠的候选碰撞对 
- `QueryAABB` / `QueryRay`:供外部进行区域索敌与射线粗筛 

零GC设计:所有输出方法均不内部 `new List` 返回, 而是由外部调用方传入预分配好的缓冲区 `results`, 内部仅做 `Clear()` 与填充 

### 1.2 ColliderPair 的状态压缩与跨格子去重设计
当一个体型较大的物体同时跨越多个网格时, 它与另一个物体可能在格子 1 和格子 2 中同时相遇, 甚至产生 `(A, B)` 和 `(B, A)` 顺序颠倒的重复配对 

为了在 $O(1)$ 时间内完成无分支去重与确定性排序, `ColliderPair` 做了两件事:
1. 强制规范化顺序:在构造函数中比较 `a.ID` 与 `b.ID`, 强制将 ID 较小的放在 `A`, 较大的放在 `B`, 彻底消除 `(A, B)` 与 `(B, A)` 的差异 
2. 64 位无符号整数状态压缩:将两个 32 位 `uint ID` 通过位运算拼接为一个全球唯一的 64 位键值:
   `PairKey = ((ulong)A.ID << 32) | B.ID`
   (注:左移前必须先将 32 位 `A.ID` 强转为 64 位 `ulong`, 否则 C# 默认对 32 位移位取模会导致位移失效) 
   有了 `PairKey`, 跨格子去重只需往 `HashSet<ulong>` 中塞入该 64 位整数即可, 同时实现了 `IComparable<ColliderPair>` 接口供第六层按 `PairKey` 进行严格确定性排序

## 2. 空间划分算法一:空间哈希 (SpatialHash)

适用场景:密集弹幕、超过怪物同处相邻位置

### 2.1 为什么用链式前向星 (CFS) 代替 Dictionary<long, List<FPCollider>>
传统的空间哈希使用字典套列表, 每帧清空重建或物体移动跨桶时, 会产生大量 `List` 对象的分配与回收, 引发严重的 GC 卡顿 

在图论中, 将“碰撞体入住哈希桶”抽象为二分图的有向边:起点 `u` 是哈希桶编号, 终点 `v` 是碰撞体 `FPCollider` 
因此直接采用一维数组链式前向星建图(边编号 `_count` 从 `1` 开始, `0` 代表空指针):
- `_head[u]`:第 `u` 号哈希桶的第一条边编号 
- `_next[e]`:同一个桶 `u` 内的下一条边编号 
- `_to[e]`:第 `e` 条边指向的碰撞体 `FPCollider` 

如果一个物体item跨越了 4 个格子, 只需对这 4 个格子的桶号分别调用一次 `AddEdge(u, item)`, 它就会分别挂在这 4 个桶的单向链表上, 全程只有整数数组赋值, 严格 0 GC并且速度极快

### 2.2 思考过程:为什么砍掉了防哈希冲突的 CellX / CellY / CellZ 数组？
早期设计中曾考虑增加三个平行数组记录每条边真实的网格坐标 `(x, y, z)`, 防止远处的两个不同格子哈希到同一个桶 `u` 中 
但经过权衡后直接将其砍掉, 理由如下:
1. 将桶容量直接开到了 `1 << 16 = 65536` 个(仅占 256KB 内存), 配合大质数异或与高位扰动 `hash ^= (hash >> 16)`, 哈希碰撞概率极低 
2. 即使极小概率下两个不同格子的物体落入了同一个桶 `u`, 在 `GetPotentialPairs` 配对时还会执行一次真实的 `a.Bounds.Intersects(b.Bounds)` 校验, 假碰撞会被当场过滤, 只多花一次 AABB 比较, 省去了维护和扩容三个大数组的内存开销,保持代码的精简与良好的可读性

### 2.3 脏桶栈 (_dirty)
下一帧到来调用 `ClearGraph()` 时, 如果用 `Array.Fill` 遍历清空全部 `65536` 个 `_head` 桶, 开销过大；而哈希算出的桶下标 `u` 是散列在 `0 ~ 65535` 之间的, 也不能只清空 `1 ~ _count` 
因此引入脏桶记录栈 `_dirty`:每次 `AddEdge` 时若发现 `_head[u] == 0`(说明桶 `u` 是本帧首次使用), 将 `u` 压入 `_dirty[_dirtyCount++]` 
下一帧清空时, 只需循环 `_dirtyCount` 次将用过的桶重置为 `0`, 并令 `_count = 1`, 即可完成整图重置 
### 2.4 边界避坑:为什么不用 pos * InvCellSize 而改用底层 64 位整除这种看似影响性能的方法?
在将世界坐标转换为网格坐标时, 如果预先计算倒数 `InvCellSize = 1 / CellSize`, 再用 `pos * InvCellSize` 向下取整, 会在特定边界出现精度截断错误 
例如:当 `CellSize = 3`, 坐标 `x = 3` 时, 定点数中 `1 / 3` 是二进制无限循环小数, 截断后再乘回 `3` 得到的是 `0.99999999976`, 向下取整 `Floor` 会错误地得到 `0` 号格子(正确应为 `1` 号格子) 

修复方案(`AxisToCell`):
直接利用 `FP` 底层的 64 位 `long Value` 进行原生整数除法(分子分母的 $2^{32}$ 缩放因子在相除时天然约分抵消):
`long q = a / b; long r = a % b; return (int)((r < 0) ? (q - 1) : q);`
不仅彻底消除了倒数截断误差, 而且原生 64 位整数除法比 128 位定点数乘法更快 

### 2.5 3D DDA 射线步进与角点相切覆盖
在 `QueryRay` 中, 若直接用射线起点和终点构造大 AABB, 斜射 100 米的射线会遍历上千个无关格子 
因此采用 3D DDA(贪心步进)算法:计算射线在 X、Y、Z 三轴跨越一个格子的距离增量 `delta`, 以及到达下一道网格墙的距离 `maxX, maxY, maxZ`, 每次挑最小的轴迈出一步 
当射线恰好穿过网格十字角点或棱边(例如 `maxX == maxY`)时, 遵循框架“相切即接触”原则, 在迈步前同步检查擦过角点的相邻格子, 并同时推进相等的轴, 防止漏检刚好贴在网格分界线上的物体

## 3. 空间划分算法二:八叉树 (Octree)

适用场景:大世界地图、空战、物体分布不均且体型差距极大

### 3.1 严格包含法(压线留父节点)的设计取舍
空间哈希在面对跨越上百个格子的巨型物体时, 会产生海量链表边 
八叉树的核心策略是:大物体住大房间(父节点), 小物体住小房间(子节点) 
我们采用严格包含法:只有当物体的包围盒完全落在某个子象限内部、不接触父节点中心十字分界线时, 才允许下沉进入子节点；一旦压在分界线上, 就直接停留在当前父节点的链表中 

这一策略带来了两个巨大红利:
1. 整棵树中, 每个物体严格只占 1 条链式前向星边(`_next` 与 `_to` 的长度仅需等于物体总数), 巨型物体留在高层节点只存 1 次, 绝不碎裂 
2. 彻底省去了 `GetPotentialPairs` 和 `QueryAABB` 中的 `HashSet` 去重开销, 因为没有任何一个物体会在两个不同的节点中重复出现

缺点也很明显:
1. 如果恰好有许多物体卡在分界线上, 按照源代码会被保留在父物体中, 极端情况下会退化为o(n^2)的两两比较算法, 对此请采用BVH空间划分算法

### 3.2 一维数组连续分配 8 个子节点 (_child[u] + i)
为了实现零 GC, 八叉树不使用 `class OctreeNode` 和指针数组 `Node[8]`, 而是将所有树节点拍平为一维数组 
每次节点 `u` 发生分裂(`Split`)时, 它的 8 个子房间一定是同时从节点池末尾连续划分(`first = _nodeCount + 1; _nodeCount += 8;`) 
因此, 不需要二维数组 `child[u][8]`, 每个节点只需存一个整数 `_child[u]`(记录头子节点的编号):
- 若 `_child[u] == 0`, 说明 `u` 是未分裂的叶子节点 
- 若 `_child[u] != 0`, 则它的 8 个子节点编号必为连续的 `_child[u] + 0` 到 `_child[u] + 7` 
保证了一个父节点的子节点必然连续, 在读取上带来的天然优势

### 3.3 位运算切盒子与原地链表指针
当叶子节点 `u` 内的人数超过阈值(`_objectCount[u] > MaxObjects`)且深度未满时触发 `Split(u)`:
1. 利用 `0 ~ 7` 的三个二进制位(`i & 1`, `i & 2`, `i & 4`)即可算出 8 个子象限盒子的 `FPBounds` 
2. 将原本挂在父节点 `_head[u]` 上的单向链表取下, 遍历每个物体调用 `GetChildIndex` 如果压线(`-1`)则重新挂回 `_head[u]`, 如果不压线(`0~7`)则直接修改 `_next[ei]` 将该边改挂到对应子节点的 `_head[target]` 上 全程不新增任何一条边(`_count` 不变), 仅靠修改链表挂钩完成下发 

### 3.4 边界避坑:中线相切漏判与越界物体处理
1. 中线相切问题:若物体 A 的右边界恰好贴在父节点中线上(`A.Max.x == center.x`), 物体 B 的左边界也贴在中线上(`B.Min.x == center.x`), 如果允许 `== center` 的物体进入左右子节点, A 和 B 就会被分进不同的兄弟节点, 而八叉树配对时不检查兄弟节点之间的碰撞, 从而漏掉这对相切接触, 因此 `GetChildIndex` 严格使用开区间(`bounds.Min > center` 且 `bounds.Max < center`), 凡是接触到中线(`== center`)的物体一律返回 `-1` 留在父节点, 通过父子祖先配对确保 100% 检出 
2. 根盒越界问题:当有物体飞出预设的 `WorldBounds` 时, 将其留在 `1` 号根节点, 并调用 `_nodeBounds[1].Encapsulate(bounds)` 动态撑大 `1` 号根节点的查询外框(而 `Split(1)` 切分八个子节点时仍以固定的 `WorldBounds` 为准), 防止越界物体在 `QueryAABB` / `QueryRay` 时因根节点剪枝而查不到 

### 3.5 DFS 祖先栈收集碰撞对
在 `GetPotentialPairs` 中, 从 `1` 号根节点执行 DFS 遍历, 并维护一个长度仅为 `MaxDepth`的祖先房间号数组 `father[depth] = cur`:
每个房间内的物体只需做两件事:
1. 与当前同一房间链表内的后续物体两两配对(`e2 = _next[e1]`) 
2. 遍历 `0 ~ depth-1` 的所有直系祖先房间 `father[i]`, 与祖先房间内滞留的大物体进行配对 
8 个兄弟子房间之间完全隔离, 无需互相检测

## 4. 空间划分算法三:动态层次包围盒树 (BVH)

适用场景:商业物理引擎标配(Box2D / PhysX / Bullet), 无世界边界限制, 支持动静分离与增量维护 

### 4.1 核心思想:不切分空间, 而是打包物体
空间哈希和八叉树都是在“切分空间”, 并且每帧调用 `ClearGraph()` 全量重建 
动态 BVH 是一棵自底向上包裹物体的二叉树, 遵循三条铁律:
1. 所有真实碰撞体 `FPCollider` 100% 存放在最底层的叶子节点中(1 个叶子严格对应 1 个碰撞体, `_left[u] == 0`) 
2. 所有内部节点(`_left[u] != 0`)不存碰撞体, 只保存刚好包住其左子节点和右子节点的外接盒子 `_bounds[u] = Union(_bounds[left], _bounds[right])` 
3. 增量维护(Fat AABB 肥包围盒):叶子节点的包围盒在物体真实 `Bounds` 基础上向四周外扩 `0.2` 米 在每帧 `Update` 时, 只要物体移动后依然被原本的肥盒子完全包含(`_bounds[node].Contains(collider.Bounds)`), 树结构就一行不动 直接跳过 只有当物体跑出肥盒子时, 才将其从树上摘下(`Remove`)并重新插入(`Insert`) 
注:微小移动未更新树结构绝不会导致漏判, 因为外扩 0.2 米的肥盒子已经提前扩大了警戒圈, 两个靠近的物体其肥盒子早已重叠并进入窄相真实 `Bounds` 比对

### 4.2 节点回收栈 (`_freeNodes`) 的必要性
由于 BVH 每帧不调用 `ClearGraph()` 重置 `_count`, 每次物体跑出肥盒子执行 `Remove` + `Insert` 时, 都会淘汰掉旧的内部父节点 `father` 并申请新的内部节点 `union` 
如果不回收淘汰的 `father` 节点, 500 个移动物体在十几秒内就会耗尽 65536 的数组容量导致内存无限膨胀 
因此维护一个数组栈 `_freeNodes`:每次 `FreeNode` 时将废弃编号压入栈顶, `AllocateNode` 时优先从栈顶弹出复用, 实现内存回收

### 4.3 SAH (表面积启发式) 插入寻路与公式化简思考过程
当新叶子 `node` 插入二叉树时, 需要从根节点 `_root` 向下寻路找到最佳同桌 `cur` 
判断标准是:插入 `node` 后, 整棵树从里到外所有内部包装盒的表面积之和增加最少(因为包装盒表面积越小, 今后被射线或查询框误碰的概率就越低) 

![思考图](docs/images\05_BHV_SAH_1.jpg)

推导与化简过程:
假设当前走到内部节点 `cur`(其左孩子为 `l`, 右孩子为 `r`), 面临三种选择:
- 选择 1(直接停在 `cur`, 与 `cur` 绑为同桌):`cur` 原本的小包装盒保留不变, 仅在头顶新增一个大盒 `Union(cur, node)` 
- 选择 2(往左孩子 `l` 走):不仅左孩子处会变成 `Union(l, node)`, 而且头顶的父盒 `cur` 为了包住新塞入的 `node`, 被迫从原来的 `cur` 膨胀为 `Union(cur, node)`, 膨胀代价为 `Union(cur, node) - cur` 
- 选择 3(往右孩子 `r` 走):同理, 右孩子膨胀加上父盒 `cur` 被迫膨胀 

把1-2拆开之后 原来的包装盒是
1 2 1-2 这三层
如果把3放外面 包装盒变成
1 2 3 1-2 1-2-3 多了一层1-2-3也就是我们的Union
而把1拆开和3结合 那么包装盒变成
1 2 3 1-3 1-2-3 此时是1-3 和 1-2-3是一样大的
由于每层包装盒都会包裹123自己 于是省略之后就是
1-2

1-3 1-2-3
这就化简为了我们为什么要比较增量

为什么代码中不能漏掉“父盒 `cur` 被迫膨胀”的代价?
如果左下角 `1` 和 `2` 离得很近(父盒 `cur` 面积很小, 为 2), 新来的 `3` 在右上角(距离极远) 若不计入毁掉父盒 `cur` 小身材的膨胀代价, 算法会误以为把右上角的 `3` 塞进左下角和 `1` 绑在一起与停在 `cur` 外面的代价一样大, 从而拆散紧凑的 `{1, 2}` 造出两个横跨全场的巨型废盒

将上述三个选择的总面积列出后, 发现三者都包含最外层的公共大盒面积 `Union(cur, node)` 在不等式两边同时减去该公共项并移项后, 复杂的继承代价公式直接化简为极其直观的三个值比大小:
- `cost_cur = _bounds[cur].GetSurface()`
- `cost_l = Union(_bounds[l], bound).GetSurface() - _bounds[l].GetSurface()`
- `cost_r = Union(_bounds[r], bound).GetSurface() - _bounds[r].GetSurface()`
若 `cost_cur` 最小则直接 `break` 停在当前节点, 否则向 `cost_l` 与 `cost_r` 较小的一侧继续下探 

### 4.4 思考过程:为什么砍掉了 AVL 树高度平衡旋转?
普通平衡二叉树(AVL / Treap)是一维键值排序树, 旋转不会破坏中序遍历顺序 
但 BVH 是三维空间聚类树 如果僅因为右子树比左子树高 2 层, 就强行做 AVL 树旋转, 会把空间上位于左下角的节点与位于右上角的节点旋到同一个父包装盒内, 造出一个横跨全地图的巨型包围盒, 导致后续剪枝彻底失效 
由于在动态 BVH 中, 移动超出肥盒子的物体本来就会通过 `Remove` + `Insert` 按最新位置重新通过 SAH 聚类寻路, 因此砍掉了平衡树高的代码
而对于既能降低树高又不会影响甚至能降低BVH表面积的复杂算法, 本套框架并未设计

### 4.5 双节点自我递归收集碰撞对 (QuerySelfDFS & QueryPairDFS)
在 BVH 中收集所有相交的叶子对, 无需借助 `HashSet`, 直接采用分治双递归:
1. `QuerySelfDFS(cur)`:一颗子树内部的碰撞, 等于【左子树内部自检】+【右子树内部自检】+【左子树与右子树交叉检查 `QueryPairDFS(l, r)`】(这三个子集完全独立, 执行顺序可任意调换) 
2. `QueryPairDFS(a, b)`:检查两棵不同子树 `a` 和 `b`:
   - 剪枝:若 `_bounds[a]` 与 `_bounds[b]` 不相交, 直接 `return` 
   - 到底:若 `a` 和 `b` 都是叶子, 检查内部真实 `Collider.Bounds` 是否相交 
   - 拆盒策略(谁大拆谁):若 `a` 和 `b` 中至少有一个是内部大包装盒, 优先拆开表面积 `GetSurface()` 更大的那个包装盒 因为大包装盒跨度广、内部空隙大, 优先将其一分为二能最快暴露出空隙, 让远离对方的一半子树在下一层递归中被立即剪枝淘汰
